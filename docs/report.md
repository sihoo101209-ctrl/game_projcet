# 탐구 보고서: MPU6050 기울기 센서를 이용한 게임 컨트롤러 제작

## 1. 탐구 동기
7월 대구한의대 '생성형 AI를 활용한 게임개발자 체험하기' 캠퍼스 탐구에서 게임 개발을 체험했다.
키보드 대신 몸의 움직임으로 조작하는 게임을 만들어 보고 싶어서, 기울기 센서로 직접 컨트롤러를 만들고
유니티 2D 피하기 게임과 연결하는 것을 주제로 정했다.

## 2. 준비물
| 부품 | 용도 |
|---|---|
| 아두이노 나노 | 센서 값을 읽어 PC로 전송 |
| MPU6050 (가속도·자이로 센서) | 기울기 측정 |
| 점퍼선, USB 케이블 | 배선, PC 연결 |
| PC (아두이노 IDE, Unity) | 펌웨어 업로드, 게임 제작 |

## 3. 원리
- MPU6050은 x, y, z 세 축의 가속도를 측정한다. 가만히 있을 때는 중력(1g)만 측정된다.
- ±2g 범위에서 1g = 16384이다. 평평하게 두면 z축 ≈ 16384, x·y축 ≈ 0이다.
- 센서를 θ만큼 기울이면 중력이 옆 축으로 나뉘어 그 축 값이 약 16384 × sinθ가 된다.
  이 값을 16384로 나누면 -1 ~ 1 사이의 기울기 값이 된다.

## 4. 회로
| MPU6050 | 아두이노 나노 |
|---|---|
| VCC | 5V |
| GND | GND |
| SDA | A4 |
| SCL | A5 |

센서와 나노는 I2C 통신(주소 0x68)으로 연결된다.

## 5. 시스템 구조
```
MPU6050 ─I2C→ 아두이노 나노 ─USB 시리얼(115200bps, "ax,ay,az")→ Unity
                                                     SerialReceiver: 문자열 → 기울기(-1~1)
                                                     PlayerMove: 기울기 → 좌우 이동
```
- 아두이노: 약 50Hz(20ms마다)로 세 축 가속도를 한 줄 문자열로 전송
- Unity: 별도 스레드에서 시리얼을 읽어 게임 화면이 끊기지 않게 함

## 6. 게임 구성
- 장르: 위에서 떨어지는 장애물을 피하는 2D 게임
- 조작: 센서를 좌우로 기울이면 플레이어가 그 방향으로 이동 (많이 기울일수록 빠름)
- 장애물에 닿으면 게임 오버, Restart 버튼으로 재시작
- 점수: 생존 시간(초)

| 스크립트 | 역할 |
|---|---|
| mpu_read.ino | 센서 값 읽고 시리얼로 전송 |
| SerialReceiver.cs | 시리얼 수신, 기울기 계산, 시작 자세 보정 |
| PlayerMove.cs | 플레이어 이동, 데드존(떨림 무시) |
| Obstacle.cs | 장애물 낙하, 충돌 시 게임 오버 |
| Spawner.cs | 일정 간격으로 장애물 생성 |
| GameManager.cs | 점수, 게임 오버, 재시작 |

## 7. 제작 과정에서 고려한 점
| 문제 | 해결 |
|---|---|
| Unity 기본 설정에서는 시리얼 통신(System.IO.Ports)을 쓸 수 없음 | Api Compatibility Level을 .NET Framework로 변경 |
| 게임 루프에서 시리얼을 기다리면 화면이 끊김 | 시리얼 읽기를 별도 스레드로 분리 |
| 9600bps는 50Hz 전송량을 감당하기 빠듯해 반응이 밀림 | 115200bps로 속도 향상 |
| 재시작하면 포트가 이미 열려 있어 다시 열리지 않고, 다시 열면 나노가 리셋됨 | 시리얼 오브젝트를 씬이 바뀌어도 유지(DontDestroyOnLoad) |
| 손 떨림 때문에 가만히 있어도 플레이어가 움직임 | 데드존(0.1) 설정 |
| 센서를 쥐는 각도가 사람마다 다름 | 시작 후 20개 값의 평균을 기준(0)으로 보정 |

실제 테스트에서 겪은 문제:

| 문제 | 해결 |
|---|---|
| 처음 쓰려던 축(ay)이 좌우 기울기 축이 아니었음 | 센서를 좌우로 기울이며 값을 측정해 ax로 변경 (9번 참고) |
| 오른쪽으로 기울이면 값이 음수가 되어 플레이어가 반대로 움직일 상황 | 방향 반전(invert) 옵션을 켬 |
| PC에 블루투스 직렬 포트(COM3, COM4)가 따로 있어 포트가 헷갈릴 수 있음 | 아두이노(CH340)가 COM6으로 잡혔고, 번호가 가장 큰 포트를 자동 선택하는 방식으로 연결됨 |
| 설치된 Unity 에디터 하나가 패키지 관리자 파일이 빠져 있어 프로젝트 생성 실패 | 같은 버전의 다른 설치본(6000.6.6f1)으로 생성 |

## 8. 생성형 AI 활용
- 아두이노·유니티 코드 작성과 오류 원인 분석에 생성형 AI(Claude)를 활용했다.
- AI가 준 코드를 그대로 쓰지 않고, 축 번호·방향·감도는 직접 테스트하며 조정했다.
- 좋았던 점: 코드를 간편하게 만들 수 있었다.
- 한계: 만들어 주는 게임의 디자인이 단순하다. 다만 이건 이미지를 직접 그리거나 가져와서 넣는 방법으로 해결할 수 있다.
  그리고 AI가 내 말을 제대로 알아듣지 못하는 경우도 있었다.

## 9. 결과
센서를 평평하게, 오른쪽·왼쪽으로 약 45° 기울인 상태에서 각각 약 60개 값을 받아 평균을 냈다.

| 자세 | ax | ay | az |
|---|---|---|---|
| 평평 | -915 | 440 | 16660 |
| 오른쪽으로 기울임 | **-12477** | 1856 | 10206 |
| 왼쪽으로 기울임 | **+11049** | -143 | 12714 |

- 평평할 때 az ≈ 16660으로 1g(16384)에 가까웠다 → 센서와 배선이 정상.
- 좌우로 기울였을 때 ax가 약 ±11000~12500으로 가장 크게, 부호가 반대로 변했다.
  45° 기울였을 때 이론값 16384 × sin45° ≈ 11585와 비슷해서 3번의 원리가 실제로 맞는 것을 확인했다.
- 좌우 기울기 축: **ax**, 방향 반전 여부: **반전함** (오른쪽이 음수이므로)
- 최종 설정값: 감도 **1.5**, 장애물 속도 **5**, 생성 간격 **0.8초** (테스트해 보니 조정할 필요가 없었다)
- 테스트 결과: 좌우 이동, 방향, 게임 오버, Restart, Restart 후 센서 유지, 점수 증가 모두 정상 동작
- 최고 점수: **128점** (점수 = 생존 시간이므로 128초 동안 버팀)

## 10. 제작 계획서와 비교
계획은 캠프 보고서의 "추가 탐구 계획"과 처음 세운 제작 순서(아두이노 → 유니티 → 테스트 → 보고서)를 기준으로 했다.

| 계획 | 실제 결과 | 달라진 점 |
|---|---|---|
| AI를 이용해 유니티 엔진으로 게임 만들기 | MPU6050 기울기 센서 컨트롤러 + 유니티 2D 피하기 게임 완성 | 계획대로 진행. 키보드 대신 직접 만든 컨트롤러로 조작 |
| 아두이노가 9600bps로 센서 값 전송 | 115200bps로 전송 | 50Hz로 보내기엔 9600bps가 빠듯해서 속도를 올림 |
| 좌우로 기울일 때 크게 변하는 축을 확인 | ax축, 오른쪽으로 기울이면 음수 | 코드 기본값(ay)을 ax로 바꾸고 방향 반전을 켬 |
| 플레이어와 장애물 모두 Kinematic | 플레이어는 Dynamic(중력 0), 장애물은 Kinematic | Kinematic끼리는 충돌(트리거)이 안 잡힐 수 있어서 변경 |
| 유니티 오브젝트를 하나씩 직접 설정 | 에디터 스크립트로 씬을 자동 생성 | 설정 실수를 줄이고 다시 만들기 쉽게 함 |
| 테스트하며 난이도 조정 | 장애물 속도 5, 생성 간격 0.8초 그대로 사용, 최고 128점 | 테스트해 보니 조정할 필요가 없었음 |
| 10월 말까지 파일과 보고서를 담임선생님께 전달 | 11월 18일 완성, 파일 전송으로 제출 | 일정이 약 3주 늦어짐 |
